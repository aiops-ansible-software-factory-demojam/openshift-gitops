The AWS demo passed the intended flow: fault playbook → alert → RCA → Forgejo issue → webhook → EDA/AO → Omnigent → PR → test-gated operator merge → one application recovery job. The app returned HTTP 403 under Enforcing before deployment, then HTTP 200 with SELinux still Enforcing. The outage alert resolved normally.

Fault-command start to observed alert resolution took **18m 28.8s**. The agent published its PR after **9m 50.3s**. Independent tests took **3m 17.2s**, and the recovery command took **1m 35.5s**. These totals include operator waiting and API preparation; they are not model-generation times.

Both AO decisions and Omnigent coding used `opencode-go/claude-haiku-5-5`, with the Anthropic transport. Model selection remains independent for the two consumers. This run made no Qwen requests.

The monitored guest and test guests ran in a dedicated public VPC in the supplied guest account, in `us-east-2`. The monitored guest was RHEL 9.6. The following improvements follow from the measured run:

- Keep the corrected consumer wrapper and publish/pin the shared provisioner release when its separate thread is ready. This removes a harness prerequisite from the agent's repair work and makes standalone dependency installation reproducible.
- Reduce repeated AAP project/inventory refreshes when revisions and guest addresses have not changed. The fault command took 57.5s for a 6.9s playbook; recovery took 95.5s for a 24.9s playbook. Preserve the collection refresh after merge and inventory refresh after guest lifecycle changes.
- Keep the exact AAP-image typing checks and Service-selector render check. Lint and syntax alone did not catch the three bootstrap boundary errors.
- Shorten the handoff's SELinux recipe once the harness is stable, keeping the incident, outcome constraints and test contract. This would test the agent's diagnosis more directly; its speed and success rate need measurement rather than a promised improvement.
- Evaluate provider-supported thinking controls separately. Reported reasoning exceeded visible output in this run, so configuration without an explicit thinking setting should not be labeled zero-thinking.

The run used the existing skill's test-only merge policy and no overall incident deadline. CNV was not exercised live on this AWS cluster. The design's full/keep-AAP platform teardown and lost-cluster receipt recovery acceptance checks have not all been completed in this run; the retained receipt does not yet provide a cleanup entry point independent of the live cluster.
